# 你不是在施法：一次「遥控建图 → 自主回放」的硬核拆解

> 主角：Odin1（激光+相机+IMU 的"黑盒子"）+ RDK X5（算力担当）+ C8T6 双驱底盘（腿脚）+ 你手里的遥控器（人肉安全帽）。
> 场景：7 米多的一条走廊/场地。你开车让它记住路，然后它自己照着重走了一遍——而且没撞。
> 本文目标：把"玄学魔法"拆成"能讲给室友听、也能对着改代码"的人话。

---

## 0. 开场泼三盆冷水（先纠正三个"你以为"）

你刚才干的事情很酷，但它跟你以为的版本，差了一点点：

| 你以为          | 实际是                                                                                                          |
| :----------- | :----------------------------------------------------------------------------------------------------------- |
| 用了 Nav2 自主导航 | **没有 Nav2**。用的是 Odin1 设备自带的 SLAM + 重定位，加一套自己写的**示教-回放**（teach & replay，纯追踪 pure pursuit）。没有代价地图、没有全局/局部规划器   |
| Odin1 是双目视觉  | **不是双目**。它是一只**单目 RGB 相机** + 一颗 **DTOF（Direct Time-of-Flight，直接飞行时间）** 深度激光 + 一个 IMU。它更像"一只蝙蝠 + 一只单眼 + 一副内耳" |
| 拔掉遥控器车才自己走   | 你拔掉的只是"人肉输入"。底盘串口那头，X5 一直在 50 Hz 喂速度指令；而**遥控器的 s2 急停优先级仍然最高**（固件里这是设计好的）                                     |

再补三个反直觉的真相，方便你之后看代码不迷路：

1. **这套系统的 TF 树里没有 `base_link`**。它直接拿 `imu` 当车体帧——"鞋"就是"脚"。如果 Odin1 没装在车体旋转中心附近，转弯就会有系统性偏差。
2. **`map` 和 `odom` 的父子关系是反着发的**：驱动发布的变换是 `odom → map`（父 odom、子 map），跟很多教科书画的 `map → odom` 反着来。tf2 不在乎方向，只要树连通就能反查，所以 `map ← imu` 照样能查。
3. **驱动根本不读 `-p config_file` 参数**（源码里写死读 `~/odin_ws/src/odin_ros_driver/config/control_command.yaml`）。你以为在跟它说话，其实它只看自己桌上那份文件——这是"玄学"的真身之一。

一句话总括：

> **你让设备先"认路"，然后你照着它的记忆开了一遍，最后车照着记忆又开了一遍。** 没有魔法，只有三个黑盒子用坐标系互相甩锅。

## 1. 第一圈：遥控它走，Odin1 在背后干啥？（建图与前向感知）

### 1.1 硬件三件套：一只蝙蝠、一只单眼、一个内耳

| 传感器         | 通俗角色                       | 实测数据（这台 X5 上）                                                                                   |
| :---------- | :------------------------- | :---------------------------------------------------------------------------------------------- |
| **DTOF 点云** | 蝙蝠的回声定位：向前打一片激光，量每束光飞回来的时间 | 256×192，约 10 Hz，原始约 4.9 万点/帧 ≈ **9.6 MB/s**（所以我们建图时把原始点云关了，只留 `cloud_slam`(经过算法精修,去噪,抽稀后的"净肉")） |
| **RGB 相机**  | 单眼：看得清颜色纹理，但**看不出远近**      | 1600×1296，10 Hz（建图时为了省 CPU 全关）                                                                  |
| **IMU**     | 内耳前庭：高频感知"我转了多少、我加速了没"     | 约 350–380 Hz                                                                                    |

为什么需要组合？因为单眼没有深度、激光没有颜色、IMU 不知道绝对位置——**三个都不靠谱，凑一起刚好能过**。这就是多传感器融合（sensor fusion）的哲学：三个学渣互相抄作业，平均分及格。

### 1.2 为什么必须让车自己完整走一圈？

SLAM（Simultaneous Localization and Mapping，同步定位与建图）是个经典的"鸡生蛋"：

- 想画地图？你得先知道**自己在哪**（位姿，pose）。
- 想知道自己在哪？你得先有**地图**。

于是它只能边猜边画：拿新一帧点云去和上一帧（或已建的小地图）对齐（scan matching / ICP 类算法），估出"我刚才挪了多少"；IMU 用高频数据补上两帧之间的抖动和旋转；后台再开一个"位姿图优化"（pose graph optimization）把误差摊匀。

问题来了：**误差像滚雪球**。你走一步估错 1 厘米，走一百步就歪 1 米——这叫**漂移（drift）**。局部看起来完美，全局已经歪到隔壁小区了。

所以**"走一圈"不是仪式感，是算法唯一可能自我纠错的机会**：只有重新看到"我见过的地方"，它才能把滚出去的雪球拽回来。

### 1.3 回环检测（Loop Closure）：给漂移的膝盖来一针

想象你喝多了在陌生小区里找路：绕了二十分钟，忽然看见一家熟悉的便利店——"哦！我回来过这儿！"

这一刻，你脑子里发生了什么？**你重新校准了整段路**：原来我以为在 A 小区，其实绕回了 B 小区，那前半段记忆全得重算。

SLAM 的回环检测（loop closure / place recognition）干的就是这事：

1. **地点识别**：这帧点云/场景像不像地图里某个老地方？（比"长得像"更狠，要比"几何结构像"）
2. **位姿图优化**：一旦确认"我刚从这儿路过"，就把整条轨迹和地图"啪"地拉直重新分配误差。

**为什么很多人回起点地图就重影/崩掉？**

- **假阳性回环（false positive）比不回环更致命**：把两条根本不像的走廊硬认成"同一个地方"，优化器会把地图拧成麻花。这就像你认错人扑上去叫前女友——后果很严重。
- **长白墙、玻璃镜子、重复的走廊**：地点识别脸盲，回环基本靠运气。
- **走太快**：帧与帧之间点云重叠不够，匹配直接摆烂。
- **急转弯**：激光扫过时运动畸变（motion distortion）没补偿好，点云糊成一团。

**你成功闭环的物理实质是什么？**

不是玄学，是三条都做到了：

1. 你真回到了起点**附近**（最后停在离起点 0.84 m 的地方）；
2. 你回去时**朝向差不多、场景没变**（没有搬家具、没有人挡着）；
3. 你**开得慢**（约 0.1–0.2 m/s），给了算法足够的重叠帧。

不过要诚实地说一句：venue2 那趟其实是 **A→B→A 的直线往返**（沿 x 从 0 开到 7.43 m 再回来），属于"往返闭环"，不是那种绕大楼一整圈的大回环。所以它的**局部一致性很好**，全局靠回程修正——这也解释了为什么第二趟的成绩会飘（见 §3.4）。

### 1.4 我们到底存下了什么？

| 产物 | 是什么 | 给谁用 |
| :--- | :--- | :--- |
| `odin_map/*.bin`（147 MB） | 设备专有格式，设备内部 SLAM 的"地图存档" | **重定位**要用它，人看不了 |
| `path.yaml` | 你开车时录的 330 个位姿点（15.66 m） | 回放时照着走 |
| `map.pcd` / `map_bev.png` / `map_info.txt` | 我们自己把点云攒出来的可视化版本（注意：到了 40 万点上限后会停止新增，所以它只是"给人看的部分"，不代表 `.bin`） | 人眼验收 |

存图不是"点一下保存"就完事：脚本往 `/tmp/odin_command.txt` 写一行 `set save_map 1`（**用文件当遥控器**），设备在后台生成、回传，日志出现 `Map transfer completed` 才算真的存好。

### 📌 课后思考 / 踩坑预警

- 走太快、转弯太急、超过 10 Hz 的"视觉盲区" → SLAM 当场失忆；
- 长走廊沿轴向漂移、玻璃/镜面产生假点云、有人搬家具 = 重影套餐；
- 建图时别开太快，也别在同一个地方反复原地扭（会给优化器递假回环）；
- 我们踩过的坑：驱动不读 `-p config_file`（以为在施法，其实在自言自语）、`save_map` 只等 8 秒就拷出半张地图。

## 2. 灵魂中枢：机器人怎么知道"我在哪"？（坐标系与 TF）

### 2.1 三种坐标：城市大地图、计步器、你的鞋

| 坐标系 | 通俗比喻 | 回答什么问题 | 缺点 |
| :--- | :--- | :--- | :--- |
| `map` | **城市大地图**（一次建图后固定不动） | "我在世界里的哪个位置？" | 只有重定位成功后才存在 |
| `odom` | **计步器坐标**（从开机那刻算起） | "相对出发，我走了多远、转了多少？" | 会漂；但连续、光滑、永不瞬移 |
| `imu`（本系统车体帧） | **你的鞋**（"我朝向哪、我歪没歪"） | 传感器/车体姿态 | 标准 ROS 里这位置通常叫 `base_link`；**这套系统没有 `base_link`，直接拿 `imu` 顶班** |
| `lidar` | 鞋上的一个外挂探头 | 雷达相对车体的位置 | 靠标定外参 |

关键理解：**`odom` 是"相对"的，`map` 是"绝对"的。** 重定位成功的那一刻，`map → odom` 这段"补丁变换"就被算出来，于是"计步器"被拉回到"大地图"上。

### 2.2 TF 不是坐标，是亲戚关系

TF（Transform）听起来很高冷，其实就是一个**实时更新的族谱 + 地址簿**：

- `map` 是爷爷，`odom` 是爸爸，`imu` 是孙子，`lidar` 是孙子手上的手环。
- 你想知道"手环在爷爷家哪个房间"，不用直接存这个答案，而是**沿族谱一段段连乘**：`map←odom` × `odom←imu` × `imu←lidar`。
- `tf2` 就是那个"帮你打听亲戚住址"的中间人。你问它 `map` 到 `imu`，它自己会在树里找路。

**为什么父子方向重要？** 因为 tf2 只要求"树是连通的"。Odin1 驱动把重定位结果发成 **`odom → map`**（父 odom、子 map），跟很多教程画的 `map → odom` 反着来——但 tf2 不在乎，它照样能反查出 `map ← imu`。这也是为什么我们的判断标准是"`map ← imu` 能查到"而不是"`map` 是根"。

### 2.3 为什么底盘有轮速里程计，SLAM 还要自己搞一套？

因为**轮子会说谎**：

- 轮速里程计（wheel odometry）：便宜、高频，但一打滑、一空转、一压到地毯，立刻开始编故事；
- SLAM/IMU 里程计：短期也会漂，但它**不怕轮子打滑**，因为它看的是"世界长什么样"，不是"轮子转了几圈"。

那为什么还要留着轮速里程计？因为它**连续、平滑、永远不会瞬移**。SLAM 偶尔会"啪"地跳一下（回环修正），轮速不会。所以工程上常见的套路是：**轮速提供平滑的短期，SLAM/地图提供准确的长期**，两者融合（EKF/UKF）。

**打滑时坐标系怎么"打架"？**

- 轮子里程计以为"我没动"，但激光发现"你明明飘了" → `odom → imu` 突然失真；
- 这时 `map → odom` 的重定位补丁会把它拽回来——就像**地图是老板，odom 是跟班，跟班跑偏了老板会喊回来**。

我们这趟的真实数据：跑完一圈，`odom` 和 `map` 差了 **0.66–0.87 m**。这不是 bug，是"计步器漂了、地图把它纠正了"。

### 📌 课后思考 / 踩坑预警

- `tf2_echo` 一开就知道谁掉线：查不到 = 树断了/时间戳不对；
- 时间戳不同步会报 `extrapolation into the future`（我们的 `tf_extra_publish_rate: 50` 就是给点云"提前量"打的补丁）；
- 拿 `imu` 当车体（而不是真正的 `base_link`），转弯时曲率会有系统性偏差——设备装得离旋转中心越远越明显；
- 同一段 TF 被两个节点同时发布 → Rviz 里鬼畜抽搐。

## 3. 第二圈：拔掉遥控，它为什么能自己走？（不是 Nav2，是"示教-回放"）

### 3.1 重定位（Relocalization）：RPG 读档后，小地图上找"我"

游戏里读档后，小地图会先闪一下，然后出现一个"你在这"的图标。重定位干的就是这个：

- 开机时它不知道自己在图里哪；
- 拿当前这一帧点云，去已经存好的 `.bin` 地图里做匹配（先全局搜索、再局部精修）；
- 我们给的初始猜测是"地图原点"（因为你会把车摆回起点），搜索半径 4 m、允许转 180°。

**判据**：重定位成功前，驱动**不发布** `map ↔ odom` 的变换；一旦成功，`map ← imu` 立刻能查到。所以脚本等的是 TF，不是等日志——这是最硬的判据。

我们的实测：重定位出来的位姿 `(0.834, −0.117)` / 朝向 +2.4°，和录制轨迹的末点 `(0.83, −0.15)` / +3.0° 差 **3 cm / 0.6°**。这相当于你凭记忆找到昨天的停车位，误差半个手机——相当能打。

> 注意：这一节讲的是**"找自己"**；它和**"怎么开车"**是两套班底，别混成一件——两者的分工，以及"为什么换个起点整条路线会平移"，见 §3.5 番外答疑。

### 3.2 我们其实没用 Nav2：示教-回放（Teach & Replay）

你问的"自主导航"，在这套系统里其实是**更土、更稳**的一招：

- `path.yaml` = 你开车时沿路撒下的"面包屑"（330 个位姿点）；
- `follow_path` = **纯追踪（pure pursuit）**：每一步盯住前方 0.35–0.8 m 的一个点，算"要打多少方向"，然后给出 `v`（速度）和 `w`（角速度）。

比喻：**它不是"看地图找路"，而是"照着你昨天的脚印走"**；前方那个点就是"你刚刚踩过的那块地砖"，它一路追着地砖跑。

所以"它为什么不会撞墙"这个问题的诚实答案是：**因为昨天你没撞**。它没有主动避障，只有"人的手"和"走过的安全路线"在兜底。

### 3.3 你问的那套 Nav2 三件套（另一个流派，先混个脸熟）

虽然这次没用，但你既然问了，就用人话讲清楚：

**代价地图（Costmap）**：把地图切成格子，每格打分。

- 黑线 = 障碍物（致命代价，别去）；
- 白线 = 可通行（代价 0）；
- 灰阶 = "有点悬"；
- **膨胀层（Inflation Layer）**：给每堵墙套一圈"社交距离结界"——离墙越近代价越高，机器人自然就不会贴着墙蹭。

**全局规划（Global Planner）**：A\* / Dijkstra / Smac，站在上帝视角出一份"战略路线"——从 A 到 B 大概怎么走。

**局部规划（Local Planner）**：DWA / TEB，处理"前面突然冒出来一只猫"的战术动作。

它俩日常互怼：

> 全局规划："照地图走近道，左转。"
> 局部规划："你礼貌吗？前面有个人在系鞋带，我先绕一下。"

**为什么这次没用 Nav2？** 三个现实原因：

1. Odin1 的地图是设备专有 `.bin`，不是 Nav2 要的 occupancy grid（栅格地图）；
2. 时间/算力优先保证"稳定跑通"；
3. 示教路线已经把"怎么走"这件事录下来了，没必要再让规划器重新解一遍。

### 3.4 为什么第二趟比第一趟差？

同一个脚本、同一个参数，两趟成绩：

| | 第 1 趟 | 第 2 趟 |
| :--- | :--- | :--- |
| 横向误差 rms | 0.103 m | 0.229 m |
| 横向误差 max | 0.423 m | 0.853 m |
| 实际最远点 | 6.50 m | 6.12 m |
| 终点朝向偏差 | 3.0° | 12.1° |

原因不是玄学：纯追踪的"前视距离"是固定的（0.35–0.8 m），**从哪个角度切进 180° 掉头，决定了它切掉多少弯**。两趟进入掉头的位姿不同，切角就不同。掉头是纯追踪的"阿喀琉斯之踵"。

### 📌 课后思考 / 踩坑预警

- 录制时的速度和回放时的 `v_max` 别差太多，否则"脚印间距"对不上；
- U 型掉头、窄门、死角 = 切角重灾区，建议掉头段单独降速；
- 动态障碍（人、猫、熊孩子）这套系统**完全没有处理能力**，只能靠人；
- 末端 `goal_tol = 0.2 m` 偏松，想让终点更准可以收紧到 0.1 m。

### 3.5 番外答疑：重定位靠"认特征"，回放靠"走路线"——这两件事为什么不矛盾？

> **你的原问题**：自主导航期间，如果起始位姿和建图时的初始位置不一致，你是让机器人"按现在的位姿走之前的动作"吗？为什么不能把初始位姿调成和建图时一致？
>
> **追问**：前面说"按建图时看到的特征点走"，这里又说"换个起点路线就平移"——到底哪个对？

**先给结论：两句话都对，只是它们说的是两个不同的工种。**

| 工种                                       | 比喻                  | 输入                    | 输出                 | 用不用"特征"？     |
| :--------------------------------------- | :------------------ | :-------------------- | :----------------- | :----------- |
| **重定位**（Relocalization）                  | 看周围建筑，认出自己在城市地图的哪条街 | 当前点云 + 保存的 `.bin` 地图  | `map ← imu`（绝对位姿）  | ✅ 用（特征/几何匹配） |
| **回放控制器**（Path following / pure pursuit） | 手机导航里那条蓝色路线         | `path.yaml` 路点 + 当前位姿 | `/cmd_vel`         | ❌ 不用         |
| **里程计**（odometry）                        | 计步器                 | 编码器/SLAM 增量           | `odom ← imu`（相对位姿） | ❌ 不用         |

一句话：**"认特征"只负责告诉你"你在哪"，"走路线"只负责"照着坐标打方向"。开车的那位不看特征，只看路线和自己的坐标。**

#### 那"换个起点路线就平移"是怎么发生的？

关键不在"用不用特征"，而在**路径文件里写的坐标系标签**：

- `frame_id: map` → 控制器问的是"我在地图哪？"，**重定位的特征匹配会把起步偏差量出来并吸收**；
- `frame_id: odom` → 控制器问的是"我相对开机位置走了多远？"，**特征匹配的结果压根没参与**；于是整条路被"挂"在你开机的位置上，换个起点，路线整体平移。

而我们第一趟录出来的就是 `odom`（原因：建图模式下设备不发布 `map` 帧，录制器只能退回 `odom`，见 §1.4）。所以"平移"不是"没用特征"，而是"**特征那一层的结果没被这条 `odom` 路径用上**"。

#### "建图时看到的特征"到底去哪了？

- 建图那趟：特征/几何被塞进设备专有的 `.bin` 地图（还有一部分成了你看到的 `map.pcd`）；
- 回放那趟：重定位用它们算出 `map ← imu`；
- 但**路径是另一份文件**（`path.yaml`），它只存路点，不存特征。

所以：**特征在地图里，路点在路径里，真正开车的是路点。**

#### 一个更贴切的类比

> 你昨天从家门口出发，沿路记了一串坐标（`path.yaml`）。
> 今天你从隔壁楼门口出发：
> - 坐标是"相对家门口的"（`odom`）→ 你照着走，整条路搬到隔壁楼门口；
> - 坐标是"城市地图上的"（`map`）→ 你先掏手机定位（重定位 = 看周围建筑认位置），导航知道你已经偏了，蓝色路线还画在正确的位置。

#### 回答"为什么不能调整初始位姿"

**能调整，但调整必须基于一次真实的测量。** 三条路：

| 做法              | 调整依据     | 结果             | 坑                         |
| :-------------- | :------- | :------------- | :------------------------ |
| A. 物理摆位（第一趟用的）  | 你把它摆回去   | `odom` 原点 = 标记 | 摆多准就多准（我们 0.17 m / 2.8°）  |
| B. 路径改成 `map` 系 | 重定位量出偏差  | 起步误差被自动吸收      | 需要重定位成功 + 验证 `map←imu` 可信 |
| C. 改配置/发假 TF    | 你嘴上说"没偏" | 它忠实地执行谎话       | 偏 1 m 它就真按没偏走 → 窄走廊撞墙     |

另外要纠正一个说法：**它不是"按现在的位姿复读之前的动作"**——开环复读的话，偏差会一直保留。它是**闭环追坐标**（§3.2）：每一拍都重新比较"我在哪 vs 路在哪"，所以 0.17 m 的摆放误差能被拐回来；但**坐标系整体换了原点**这种系统性偏差，闭环也救不了——它只会忠实地把整条路平移。

#### 📌 课后思考 / 踩坑预警

- 不是"特征没用"，是"特征的结果没被这条 `odom` 路径消费"；
- 想吃到"认特征"的红利：把 `path.yaml` 的 `frame_id` 改成 `map`（前提：重定位成功，且 `map←imu` 与录制末点吻合——我们实测差 3 cm / 0.6°）；
- 起步点离路径太远（超过最近点搜索窗口 200 个点）→ 可能锁错参考点，甚至一上来就判"走完"；
- 重定位失败时 `map` 系不可用，只能退回"物理摆位 + `odom`"。

## 4. 硬核破壁：关键指令与话题，都在"谁向谁喊话"

### 4.1 全景数据流（一张图看懂）

```text
        ┌──────────────┐   USB3 (点云/图像/IMU)   ┌──────────────┐
        │   Odin1      │ ───────────────────────► │   RDK X5     │
        │ 激光+相机+IMU │                          │  ROS2 大脑    │
        └──────────────┘                          └──────┬───────┘
                                                         │ 9 字节串口帧 @50Hz (USART1)
                                                         │ 7 字节状态帧 @10Hz
                                                         ▼
                                                  ┌──────────────┐
                                                  │  C8T6 仲裁员  │  10 ms 一次裁决：
                                                  │  固件 10ms tick│  s2急停 > 串口 > 遥控 > 停
                                                  └──────┬───────┘
                                                         │ CAN 扩展帧 0x1314 @250K，10 ms
                                                         ▼
                                                  ┌──────────────┐
                                                  │ 双驱控制器    │──► 左右电机
                                                  └──────────────┘
```

### 4.2 四个关键"喊话"

**① `/cmd_vel`（`geometry_msgs/Twist`）—— 老板对司机**

- 谁发：`follow_path`（20 Hz，算出来的 v/w）或者你的键盘遥控；
- 谁听：`bridge_node`；
- 背后：桥接节点把 `v=0.10 m/s` 换算成指令单位（±1000），组 9 字节帧，50 Hz 往串口灌；C8T6 收到后 10 ms 一次转发成 CAN 帧。
- 一句话：**"我让你以多少速度、多少角速度走"**，最后落地成电机能听懂的 8 个字节。

**② `/car/status`（`std_msgs/String`，里面是 JSON）—— 门卫的状态汇报**

- 谁发：`bridge_node`（数据来自 C8T6 的 10 Hz 上行帧）；
- 谁听：你、`follow_path`（安全联锁）；
- 关键位：`can_ack`（CAN 真的通了）、`rc_ok`（遥控在线）、`estop`（s2 急停）、`src`（当前谁在开车：serial / rc）。
- 一句话：**"底盘还活着吗？谁在开车？急停了吗？"** 这是我们排查时的"体检报告"。

**③ TF `map ← imu` 与 `/odin1/odometry` —— 定位的"官方口径"**

- TF 回答"我在世界地图哪里"；`/odin1/odometry` 是设备吐的位姿原文（在 `odom` 系）；
- `tf2_echo map imu` 一开，就知道重定位有没有成功、车离起点多远；
- 一句话：**TF 是"亲戚住址"，odometry 是"计步器读数"**。

**④ `/odin1/cloud_slam` 与 `/tmp/odin_command.txt` —— 点云与"文件当遥控器"**

- `/odin1/cloud_slam`：10 Hz 的 SLAM 点云，`map_from_cloud` 攒成 PCD / 俯视图；
- `/tmp/odin_command.txt`：写一行 `set save_map 1` 就等于按了设备上的"存图"按钮——**用文件当遥控器**，这是这套驱动的祖传设计。
- 一句话：**"把看到的世界给我看" + "存一下，谢谢"**。

### 4.3 我们的脚本，翻译成人话

| 脚本                 | 干了什么（人话版）                                                                                           |
| :----------------- | :-------------------------------------------------------------------------------------------------- |
| `start_mapping.sh` | 把 Odin1 配置改成建图模式 → 启动驱动 → 再拉三个后台：点云导出、轨迹录制、底盘桥接。**桥接会 50 Hz 发零帧压住遥控器**，所以遥控开车前要 `pkill bridge_node` |
| `save_map.sh`      | 给设备写"存图"小纸条 → 等日志说"传完了" → 把 `.bin` 拷进建图目录<br>一般情况下odin 1是不会把数据传回x5中,这个文件是强制其将数据传回                   |
| `stop_mapping.sh`  | 按顺序 Ctrl-C：先让节点把点云/轨迹吐到磁盘，再停驱动（顺序错了会丢文件）                                                            |
| `start_relocal.sh` | 生成重定位配置 → **写进驱动真正读的那个文件**（它不认 `-p config_file`！）→ 启动 → 等 `map ← imu` 出现                            |
| `drive_lap.sh`     | 检查桥接和定位 → 启动 `follow_path` 纯追踪 → 到终点做朝向修正、打印误差、存实际轨迹                                                |


### 📌 课后思考 / 踩坑预警

- **桥接节点 50 Hz 发零帧会"压住"遥控器**：固件仲裁里串口优先级高于遥控，这是设计（跑建图/回放时人松手更危险），不是 bug；
- **驱动不读 `-p config_file`**：所有模式/地图配置都要写进它真正读的那个文件（我们因此白等了 90 秒"重定位失败"）；
- **话题存在 ≠ 有数据**：`sendcloudrender: 0` 时 topic 还在，但永远没有数据，别被 `ros2 topic list` 骗了；
- **estop 需要遥控数据新鲜**：接收机掉线时 `estop` 会变成 false——不是"解除急停"，是"没人能急停了"。**自动跑之前务必确认 `status` 里 `rc_ok` 在**。

## 5. 一分钟复盘 + 术语小抄

### 你今天真正学会的四句话

1. **建图 = 边估位姿边画地图，误差会滚雪球；回环是唯一的"后悔药"。**
2. **定位 = 三套坐标系互相甩锅：`map` 是老板，`odom` 是跟班，`imu` 是鞋。TF 就是族谱。**
3. **自主走 = 没说"去那边"，而是"照着我昨天走过的脚印再走一遍"。**
4. **"认特征"和"走路线"是两个工种**：前者回答"你在哪"，后者照着坐标打方向；路径写 `odom` 就认开机点，写 `map` 就认地图——这就是"换个起点为什么整条路线会平移"的全部真相（详见 §3.5）。

## 6. 明天可以怎么升级（按性价比排序）

1. **标定速度**（`calibrate_speed`）：现在 `mps_at_max=0.8` 是猜的，`VMAX=0.10` 到底多快没人知道；
2. **掉头段单独限速 / 变前视**：这是第二趟成绩变差的主因，改动小、收益大；
3. **把第一圈的路线录成真正的环线**：走完整场地一圈回起点，回环质量会明显好于直线往返；
4. **加轮速里程计 + EKF**：让"计步器"更硬；
5. **上 Nav2**：把点云转成栅格地图（occupancy grid），接 `costmap` + 全局/局部规划，才能处理动态障碍——这是大工程，但也是"真·自主导航"的门票。
