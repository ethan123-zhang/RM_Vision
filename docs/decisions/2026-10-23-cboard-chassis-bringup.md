# C 板底盘沿用官方 17.chassis_task，另加调车层

- 日期：2026-10-23
- 状态：已采纳
- 关联：`cboard_chassis/`、`PROGRESS.md` 里程碑 10

## 背景

本赛季底盘换成 C 板 + 4×M3508/C620，轮子从麦轮改成 **4 轮全向**。
手上有官方 `Development-Board-C-Examples-master`，其中 `17.chassis_task` 是一套完整的
四轮底盘工程：CAN 收发、麦轮解算、速度环 PID、遥控器状态机、FreeRTOS 任务划分都有。
用户要求“整体框架是官方的，最好不要变，代码在这个框架上加”。

第一次上电的三个现实障碍：

1. `chassis_task` 里有 `while (4 个电机 || DBUS 掉线)` 的**死等**，任一设备没通就永远不往下走；
   而 RGB 灯照常流动，看起来像“板子活着”，实际一个 CAN 包都没发。
2. 遥控器不在线时主循环只发 0 电流，**没法单独验电机**。
3. 四个 C620 的 ID→轮位、轮子正反在代码里写死（按官方标准车、麦轮装法），
   换成全向轮和新车以后必然对不上，但没有任何手段能看出是哪一个错了。

## 选项

| 选项 | 优点 | 缺点 |
| :--- | :--- | :--- |
| A. 直接在官方工程里改参数 | 改动最少 | 官方文件被污染；换车/换线后要再改一次；仍然看不见失败点 |
| B. 拷贝官方工程 + 调车层（选定） | 官方解算/PID/状态机一行不动；标定与业务解耦；能单验电机 | 多一层代码；多两帧调试 CAN |
| C. 自己重写一套底盘框架 | 最自由 | 偏离用户要求，丢掉官方已调好的 PID/状态机 |

## 结论

选 B。`cboard_chassis/` 是 `17.chassis_task` 的完整拷贝，改动只有：

- `chassis_task.c` 5 处 `[BRINGUP]` 插入；
- 新增 `chassis_bringup.{c,h}`（扫描模式、调试 CAN 帧、带超时的等待）；
- 新增 `chassis_bringup_map.{c,h}`（轮位↔CAN ID↔方向标定表 + 扫描时序，纯逻辑、可主机测试）；
- Keil 工程挂两个源文件。

全向轮**沿用同一套解算**：4 轮全向 45° X 型与麦轮的轮速符号完全相同，只差 1/√2 系数，
官方公式直接可用（给定 1 m/s 实际约 1.41 m/s，属已知偏差，接导航前再统一单位）。

## 理由

- 用户明确要保留官方框架，B 是唯一满足“框架不变 + 可标定”的选项。
- 把“物理轮位↔CAN ID↔方向”抽成表，标定一次以后换线、换电机都不用动公式。
- 把扫描时序与映射做成纯函数，可以用 gcc 在 PC 上跑四套标定表的断言（171 项），
  不用等硬件就能证明“换表只改数据、不改行为”。
- 调试通道只有 USB-CAN 分析仪（无 USB-TTL）：把状态编码进 `0x1F0`/`0x1F1` 两帧，
  分析仪直接可读，不需要额外硬件，也不需要 USB CDC（工程里没有 ST 的 USB 库）。

## 影响

- 启动行为变化：不再死等，3 s 超时后继续跑；标定表非法时响三声且四路电流恒 0。
- 总线上多 `0x1F0`（25 ms，四路 rpm）与 `0x1F1`（100 ms，状态）两帧，占带宽约 5%。
- 默认 `CHASSIS_BRINGUP_MODE = SWEEP`：**烧进去车不会听遥控器**，只会按 ID 扫。标定完必须改 0。
- 新增纯逻辑测试入口 `cboard_chassis/tests/run_tests.ps1`。

## 复审条件

- 若实测发现全向轮不是 45° X 型（侧推不能平移），解算需另写，本决策的“沿用解算”部分失效。
- 若后续接入 X5 串口控速，需要给 `vx/vy/wz` 定真实单位，速度常数要按 0.7071 修正。
- 若 C620 的 ID 不再是 1~4（改用 5~8、或 `0x1FF` 控制帧），扫描模式与 TOE 索引都要跟着改。
