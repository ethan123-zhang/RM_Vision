# 遥控器 DBUS 收不到：有字节但没有 18 字节 0xA9 帧

- 日期：2026-10-22
- 环境：RDK X5 Ubuntu 22.04 / C8T6 STM32F103C8T6 / DT7 遥控器 + 接收机（型号待确认）/
  SN65HVD230 + XHSMCUW50 / CH340 USB-TTL
- 关联：`car_slam_lap/WIRING.md`、`car_slam_lap/README.md` §11、
  `firmware/C8T6_DT7_car/Hardware/UART/DBUS.c`

## 现象

X5 的 `/car/status` 一直只有：

```json
"status": 19,
"flags": ["can_ok", "link_ok", "can_ack"],
"src": "serial"
```

没有 `rc_ok`。烧了带调试位的固件后变成：

```json
"status": 51,
"flags": ["can_ok", "link_ok", "can_ack", "uart2_rx"]
```

即 **USART2 收到过字节，但从未凑成完整 18 字节 DBUS 帧**（`dbus_frame` 不置位）。

## 复现步骤

1. 接收机 5V 供电、LED 常亮（已对频）、遥控器开机；
2. 信号线接 C8T6 **PA3**（USART2_RX），共地；
3. X5 起 `bridge_node --port /dev/ttyS1`；
4. `ros2 topic echo /car/status`，`rc_ok` 始终不出现；
5. 调试固件 `status=51`，`uart2_rx=1`、`dbus_frame=0`。

## 排查过程

已确认：

| 项 | 结果 |
| :--- | :--- |
| 接收机 LED | 常亮（已对频） |
| 信号线 | 接 PA3（USART2_RX） |
| 接收机端口 | 标称 DBUS |
| 共地 | 已补，接收机与 C8T6 共地 |
| PA3 空闲电压 | 3.3V 左右（注意：PA3 有上拉，可能掩盖接收机真实输出） |
| USART2 字节 | 调试位 `uart2_rx=1`，确实有字节 |
| 完整 DBUS 帧 | `dbus_frame=0`，没有 |

USB-TTL 抓包（CH340，COM15，**100000 8E1**，3 秒 3857 字节）：

```text
00 04 20 00 01 78 00 00 00 00 00 00 00 00 00 00 00 04
00 04 20 00 01 78 00 00 00 00 00 00 00 00 00 00 00 04
...
```

- **18 字节一个周期**（当时误以为这就是"18 字节含帧头"的 DBUS 帧长，其实这 18 字节是纯通道数据）；
- 但全程 **没有 `A9`**，也没有 SBUS 的 `0F`；
- 换 115200 后字节值变成 `00 0C 40 00 01 F0...`（随波特率缩放），说明读到的可能是被错误采样的脉冲/反相信号。

## 根因

**接收机本身没问题，是固件的分帧方式错了：这一款接收机的 18 字节帧首没有 `0xA9`。**

`_extract/ttl.bin`（2026-10-22 16:12 抓的 1026 字节，100000 8E1）逐字节看：

- 周期严格是 **18 字节**（57 帧 × 18）；
- 全部 1026 字节里 **`0xA9` 出现 0 次**；
- 只有 5 种字节值：`00 01 04 20 78`（摇杆没动，所以帧内容恒定）；
- 按 `DBUS.c` 的位布局解这一帧：`ch0..ch3 = 0,0,0,0`、`s1=1`、`s2=3`
  —— 正好是"摇杆居中 + s2 打在急停档"，说明数据是**对的**，只是没有帧头。

而 `DBUS_OnByte()` 只在 `s_cnt == 0` 时接受 `0xA9`，其余字节当场丢弃。
既然帧首永远不是 `0xA9`，就一个字节也攒不进缓冲区：

- `uart2_rx=1` —— 有字节（中断确实在跑）；
- `dbus_frame=0` —— **上电以来一帧都没凑成**（不是偶尔掉帧）；
- `rc_ok=0` —— 自然也没有。

`status=51`（0x33）正好是 `can_ok|link_ok|can_ack|uart2_rx`，缺的两位就是证据。
标准 DR16 的 DBUS 确实是 `0xA9` + 18 字节；这一款不是标准 DR16（型号待确认），
不能按标准帧头去卡。

## 解决

`Hardware/UART/DBUS.c` 改成**空闲间隔定界**：

- 帧内字节间隔只有 0.1 ms（100000 baud），帧间空闲约 12 ms，`>2 ms` 就判定
  上一帧结束、当前字节是新帧首。不再要求 `0xA9`；
- 仍兼容标准变体：一段突发是 19 字节且首字节为 `0xA9` 时剥掉帧头再解；
- 防止 PA3 噪声凑假帧：18 字节里 `p[6..16]` 必须全 0（实测帧的保留字节恒 0，
  随机字节同时为 0 的概率≈0）；
- 新增 `tests/dbus_frame_test.c`：实测帧、带帧头变体、半帧重同步、噪声拒绝、
  摇杆偏移、超时判活共 **46 项断言**；`run_tests.ps1` 已接入。

Keil AC5 实编译：`Code=11152 RO=312 RW=76 ZI=1332`，**0 Error / 0 Warning**，
hex 已重新生成。

## 补记：s1/s2 的 0 是合法档位（2026-10-22 晚）

第一版为了防噪声，额外要求 `s1/s2` 必须为 1/2/3。实机一扫就翻车：这台遥控器的
`OFF` 档在接收机里编码成 **0**，于是切到 OFF 后整帧被当成噪声丢掉，`/car/status`
从 127 变成 115（`rc_ok` 直接消失）——看起来像"接收机断了"，其实是自己把合法帧
杀掉了。已删掉这条判据：**s1/s2 允许为 0**，防噪声只保留"保留字节必须全 0"。

## 验证（2026-10-22 20:20，实车通过）

- 烧 `C8T6_CAN_car.hex` 后 `/car/status` 稳定 `status=119`
  （`can_ok|link_ok|rc_ok|can_ack|uart2_rx|dbus_frame`）；
- 停掉 `bridge_node` 后 `src=rc`，遥控器能驱动轮子，方向正确；
- **S2 三档实测定稿**：GPS(上)=1 全速 / 中间 ATTI=3 **1/3 速** / 下面 ATTI=2 **急停**
  （急停时 `status=127`）；`rc.s1`（OFF/CL/HL）不参与控制；
- 中途出现"遥控突然没数据"，最后定位是**接收机信号线松动**，与固件无关。
  `dbus_frame` 是锁存位会掩盖这种掉线，所以把 `uart2_rx` 改成了 **500 ms 实时位**。

若换一台接收机仍没有 `rc_ok`，再查校验位（8E1 vs 8N1）：本抓包是在 8E1 下读的，
若接收机实际是 8N1，MCU 会把偶校验字节（`0x00`/`0x78`）按 PE 丢掉。
验证方法：把 `usart.c` 的 `UART_PARITY_EVEN` 改成 `UART_PARITY_NONE` 再烧，
或逻辑分析仪量第 9 位（偶校验字节应为 0，8N1 的停止位应为 1）。

## 可复用结论

- **"TTL 能读到"不等于"MCU 能解"**：先对齐两边对帧的定义（帧头/长度/校验位），
  再怀疑线；`uart2_rx`（收到过字节）和 `dbus_frame`（凑成过整帧）两个调试位
  就是为这个区分的，比盲猜快得多；
- **帧头不是所有 DBUS 接收机都有**。标准 DR16 是 `A9` + 18 字节；克隆/第三方
  接收机可能只发 18 字节数据。用帧间空闲定界比死等帧头稳，还顺带兼容两种；
- 用**抓包字节数反推帧长**：1026 = 57×18、3857 = 18×214+5，比"看起来像 18"可靠；
- **PA3 有上拉**时，量 PA3 电压不能判断接收机是否反相，要量接收机信号脚；
- CH340 在非标准波特率（100000）下可能不准，优先用 CH343/CP2102 复核。
